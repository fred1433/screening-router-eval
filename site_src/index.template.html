Open-model routing for screening recommendations

The question: Can a smaller open-weight model prepare a defensible screening recommendation, and when does calling a larger model actually improve it, while preserving analyst sign-off?

Run v1 covered {{n_test}} unseen records from the same {{n_families}} authored case families, each run {{reps}} times. Correct and supported among answerable runs: small model {{small.supported_on_answerable.kn}}, large model {{large.supported_on_answerable.kn}}, router {{router.supported_on_answerable.kn}}. No configuration recommended excluding a true match: none of {{n_true}} true-match cases in any run, a 95% interval of 0 to 7%. Scored on five separate dimensions, the same answers still carry faults the decision score hid: next actions with authorizing language, and evidence cited from the wrong line. A stricter citation check added after the run would send back {{cr.small}} small-model outputs, {{cr.large}} large-model outputs and {{cr.router}} router outputs.

Against the small model alone, the router won {{gain.runs}} runs over {{gain.cases}} cases and lost {{loss.runs}}, at a resource index of {{router.index}} against 1 and a p95 latency of {{router.p95}} against {{small.p95}}. Against the large model alone it used a resource index of {{router.index}} against {{large.index}}. Stopping the router before its large-model call gives {{abl.kn}}, so the large-model step accounts for {{router_minus_abl}} runs.

Controls v2 were written after inspecting the v1 results, so on these {{n_test}} cases v2 is not a measurement on unseen data. Replayed on the recorded answers without a new model call, they leave the router at {{v2.router.correct}} correct and supported and send {{v2.pending_total}} runs back for a repair call that was not made. {{new.n}} new cases generated after the v2 freeze are the unseen test; so far only the rules have run on them.

Scope: the identity disposition for a list candidate already selected upstream; adverse media, risk scoring and PEP screening are out. Customer records are synthetic. Candidate records are copied field by field from the OFAC SDN export published {{published}}, with the entry UID kept; nothing is alleged about anyone. Models: {{small_model}} on {{small_endpoint}} and {{large_model}} on {{large_endpoint}}, through OpenRouter with fallbacks disabled. The page as first published is kept at v1.

Case files, as the analyst would receive them

Each file holds the customer documents, the list candidate, the proposed disposition with its citations, the route, every check in order and the next action. Each dimension is scored on its own, so a right decision can sit next to evidence or a next action that still needs correcting. Nothing is approved by the system.

What v2 changes, and the new cases

Controls v2, written after reading v1

  • One test for an absent value on both sides, so not listed never conflicts; the rules' output now crosses the same validator as the models'.
  • For a supported match the next action is fixed text: review and refer for the sanctions decision; it never authorizes onboarding. Authorizing language is rejected everywhere else.
  • Code computes exact and listed alias; a model claim the code does not confirm sends the router to the large model, and a name that normalises to nothing stops for a person.
  • Evidence is bound to its field and to the customer: a Residence country line does not prove a nationality, a sentence about a brother proves nothing about the customer.
  • {{tests_passed}} of {{tests_total}} tests pass, including one showing the four configurations cross the same validator.

What this does not show

  • Performance on real customer files. The customers are synthetic and the case families were authored by the builder.
  • Expert agreement. References were checked by a fresh model session, not by a compliance analyst.
  • v2 on unseen data with models. On the {{n_test}} v1 cases v2 was written after reading the results; on the {{new.n}} new cases only the rules have run.
  • A self-hosted deployment. Only the hosted endpoints were tested.
  • A frozen v1 case set in every detail: the relative-trap notes said elder even for a relative born after the customer; the {{rerun.cases}} held-out cases it touched were re-run with the frozen pipeline.
