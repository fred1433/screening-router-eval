Open-model routing for screening recommendations

The question: Can a smaller open-weight model prepare a defensible screening recommendation, and when does calling a larger model actually improve it, while preserving analyst sign-off?

On {{n_test}} held-out cases, each run {{reps}} times, a small open-weight model behind shared checks did as well as a large one: {{small.correct_supported}} and {{large.correct_supported}} of {{rows}} runs correct and supported, and neither recommended excluding a true match. The router reached {{router.correct_supported}} of {{rows}} with no needless stop, calling the large model on {{esc.n}} runs and using a resource index of {{router.index}} against {{large.index}} for the large model alone.

The checks did the protective work, not the model size. The large model's first answers made {{fa.large.wrong_excl}} such errors; after one repair call, neither model recommended excluding a true match in any run.

What I would recommend from this run: the small model behind deterministic checks as the default path, and the large model only for named, observable reasons. The router's gain over the small model alone is real but narrow here ({{small_needless_cases_word}} case, three runs); it earns its place by removing needless stops at a fraction of the large model's cost.

Scope: the identity disposition for a list candidate already selected upstream; adverse media, risk scoring and PEP screening are out. Customer records are synthetic. Candidate records are copied field by field from the OFAC SDN export published {{published}}, with the entry UID kept; nothing is alleged about anyone. Reference answers were written by the builder and checked by a separate model session, not by a compliance expert. What this run does not show

  • Performance on real customer files. The customers are synthetic and the families of difficulty were chosen by the builder.
  • Expert agreement. The references were checked by a fresh model session that did not build them; a compliance analyst has not reviewed them.
  • A self-hosted deployment. Latency and resource use are measured on hosted endpoints on {{run_date}}; the harness takes any OpenAI-compatible endpoint, but only the hosted one was tested. OpenRouter model names are aliases the host can update.
  • The search that selects the candidate. It is assumed done upstream.
  • Completeness of the missing-information list on a decided case. The score checks the disposition, the conflicts and the claimed agreements; an incomplete list of missing items is not penalised.

On fine-tuning, this run gives no reason to train yet. The remaining errors are of three kinds, and two belong in code: a disposition that does not follow from the model's own correct comparisons (code can apply the policy), and a field marked not captured read as a conflict (a one-line rule). Only the third, an attribute read as another (residence as nationality, nationality as place of birth), is something training might touch. The memo says which of those training could touch, what reviewed data it would need and which held-out experiment would decide it.
